# Safe-to-Spend calculation

Safe-to-Spend answers one question: *how much can I spend right now without missing
something I already owe?* It is a deterministic, fully auditable subtraction — no model, no
statistics, no rounding surprises. The LLM may explain the result; it never computes it.

- Inputs and assembly: `backend/app/services/safe_to_spend.py`
- Pure arithmetic: `backend/app/calculations/safe_to_spend.py`
- Endpoint: `GET /api/v1/safe-to-spend` (and `GET /api/v1/safe-to-spend/category/{id}`)

## The formula

```
raw = eligible_balance
    − pending_debits
    − bill_reserves
    − loan_reserves
    − credit_card_reserves
    − explicit_reserves
    − savings_reserves
    − minimum_buffer

safe_to_spend = max(raw, 0)          projected_shortfall = max(−raw, 0)
```

Every term is money in cents-precision `Decimal`; there is no floating point in the engine.

| Term | Meaning | Double-count protection |
| --- | --- | --- |
| `eligible_balance` | Sum of active, non-liability accounts with `include_in_safe_to_spend`. | A savings account excluded from spending simply is not counted. |
| `pending_debits` | Pending outflows from those accounts until they post. | Ignored when the pending transaction is a transfer between two eligible accounts, or when the user disabled pending debits. |
| `bill_reserves` | Unpaid bill occurrences inside the horizon, at their **remaining** amount. | Same occurrence cannot also appear as a loan instalment. |
| `loan_reserves` | Loan/advance instalments inside the horizon. | Instalments already settled by a confirmed repayment are dropped; a loan recorded as a bill keeps only one entry. |
| `credit_card_reserves` | Minimum payments the owner typed in. | Credit *limits* are never available cash; card repayments are transfers, not purchases. |
| `explicit_reserves` | User-created reserves and commitments. | Reported individually so the user can remove them. |
| `savings_reserves` | Protected `virtual` savings plus planned contributions inside the horizon. | An account-backed goal whose account is already excluded protects nothing extra ([details](savings-goals-and-allocations.md)). |
| `minimum_buffer` | The cash floor the user wants to keep. | Clamped at zero; it is a debit, never a credit. |

## Horizon

`planning_horizon()` ends at the **next payday** when one is known, capped by
`safe_to_spend_horizon_days` (default from settings, clamped to
`max_safe_to_spend_horizon_days`). Without a payday it is simply today + horizon days.
This is why the response carries both `horizon_end` and `payday`: a number that only covers
today is not the same answer as one that covers the days until money arrives.

## Transparent breakdown

The response is designed to be read, not trusted blindly:

```json
{
  "eligible_balance": "2500.00",
  "pending_debits": "0.00",
  "bill_reserves": "0.00",
  "loan_reserves": "0.00",
  "credit_card_reserves": "0.00",
  "explicit_reserves": "0.00",
  "savings_reserves": "0.00",
  "minimum_buffer": "200.00",
  "raw_amount": "2300.00",
  "safe_to_spend": "2300.00",
  "projected_shortfall": "0.00",
  "obligations_total": "0.00",
  "accounts": [], "bills": [], "loans": [], "savings": [], "credit_cards": [],
  "reserves": [], "pending_items": [],
  "warnings": ["…"],
  "explanation": [
    { "key": "eligible_balance", "label": "Available in spending accounts", "amount": "2500.00", "kind": "credit", "detail": "Everyday Checking" },
    { "key": "minimum_buffer", "label": "Minimum cash buffer you want to keep", "amount": "200.00", "kind": "debit", "detail": null },
    { "key": "safe_to_spend", "label": "Safe to spend now", "amount": "2300.00", "kind": "result", "detail": null }
  ],
  "stale_information": false
}
```

`explanation` is generated by the same function that does the arithmetic, so the lines always
add up. Each contributing account, bill, loan, card, savings goal and pending item is listed
with its own amount.

## Staleness and warnings

`stale_information` is true when there is no transaction in the last 45 days
(`MAX_STALE_DAYS`), and the result says so in `warnings`. Other warnings are emitted for:

- no spending account contributing;
- a liability accidentally marked as contributing (credit cards never count as cash);
- pending debits included as deductions.

Stale data is never hidden: the UI shows a warning banner next to the figure.

## Categories

`safe_to_spend/category/{category_id}` reuses the overall horizon and subtracts that
category's own unpaid bills and spending so a category answer matches the headline number.
It is a convenience view, not a second engine.

## What is deliberately not in the number

- Credit limits (never available cash).
- Expected future income beyond the buffer/payday horizon logic — income is shown separately
  in [obligations](unified-financial-obligations.md) and never netted against debts.
- Any projection of spending behaviour. Safe-to-Spend is what is left after commitments, not
  a forecast of what the user will do.
